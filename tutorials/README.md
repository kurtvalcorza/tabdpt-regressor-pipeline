## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6) and isolated environment (RUN1, RUN10, ENV6):** the primary path performs no clone, repository install or repository import, and installs nothing into the notebook kernel. Section 2 of the notebook writes the package under `src/tabdpt_regressor_pipeline/`, the notebook's stage runner, the hash-locked `requirements-colab.lock.txt`, the snapshot manifest and the licence into a run directory and verifies each against its SHA-256 (`CARRIED_HASHES`); a pinned `uv` wheel (size + SHA-256) builds a managed-CPython virtual environment from the lock with `--require-hashes`, keyed on the lock's digest so a second Run all reuses it, and every learner cell runs one stage of the stage runner in its own process (`run_stage`). Re-running the Section 1 cell keeps the run directory. `metadata.dimer.generated_from` records the repository, the generating commit, the package SHA-256, the carried-file digests and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when a carried file (package module, stage runner, lock, manifest) differs from the repository, when the lock does not pin every `pyproject.toml` runtime pin with hashes, or when a notebook is not byte-identical to the generator's output for its template.
- **Model acquisition:** the `weights` stage writes the carried manifest into the snapshot directory under `weights/`; `stage_missing_files(..., allow_download=True)` fetches only the manifest entries that are absent, at the immutable revision (never `main`); `verify_snapshot` re-hashes them; each later stage builds its pipeline from the verified snapshot. The notebooks' only external dependencies are PyPI (the `uv` wheel and the locked packages), the managed CPython build `uv` downloads, and the model host at that revision.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/<stem>_input_manifest.json` with the schema, observed table structure and target summary, verdict and one recorded rejection finding; `evaluation_report` (EVAL21) writes `outputs/<stem>_evaluation_report.json` — `sample-sanity` with `mae` / `rmse` / `r2` and the training-mean baseline.
- **External-artifact section (§19.1, XAS1–XAS7, SART1–SART11; replaces the companion, KND11):** Section 10 needs only the setup cells; by default it downloads the pinned release asset `sample-artifact-diabetes-v1` (v1: packed on the VM after a recorded hosted T4 run of this notebook's default path at `1e816d9`, from that run's exported `outputs/artifact/`, which does not meet SART9 under the owner ruling of 2026-10-22; it stays pinned until `sample-artifact-diabetes-v2`, the ZIP the export stage writes in a recorded run, is published and pinned), refuses it unless its SHA-256 equals the pinned digest, extracts exactly `artifact.json` and `training_context.parquet` (no directory, `..` or symlink member), checks that its feature columns and target column equal the diabetes default path's (SART10; a regression artifact has no label set), reconstructs through `load_verified_artifact` without refit (failing closed on the legacy path), and writes predictions and provenance under `outputs/external_artifact/`. ## Preprocessing and capacity semantics

For TabDPT, `fit()` performs preprocessing fitting plus **in-context support conditioning**, not gradient fine-tuning. The repository feature encoder preserves numeric columns and deterministically maps categorical values, using separate fitted codes for missing and unseen categorical values. Upstream TabDPT uses a training/support-fitted mean imputer for numeric missing values and standard scaling. If encoded feature width exceeds the loaded model's `max_features`, the upstream configured feature-reduction path is surfaced by the tutorials; `context_size` separately limits support rows used during prediction.

The E2E notebook reports input shape/missingness, model feature ceiling, whether feature reduction activates, requested context size, and the effective upper bound on support rows. The artifact-inference notebook reports the same serving-relevant capacity information for an externally supplied artifact and validates new numeric data so non-numeric or infinite values do not silently become imputed values.

## Artifact contract and trust boundary

The reusable DIMER serving state includes the labelled support table, fitted repository encoder state, fitted upstream imputer/scaler state, any fitted PCA basis needed for wide tables, and the exact pinned base-model contract.

`export_artifact_bundle()` emits an explicit v3 release artifact. `validate_artifact_bundle()` checks artifact format/task, fitted preprocessing consistency, support-table path/size/SHA-256, and the declared base-model repository/revision/filename/digest/upstream commit before model loading. `load_verified_artifact()` reconstructs new release artifacts from saved fitted preprocessing state **without fitting those preprocessing statistics again**.

Established older `tabdpt-dimer-context-v3` manifests that predate the additive explicit version/semantics/size fields remain compatible. If such an artifact lacks the complete fitted upstream preprocessing state, `load_verified_artifact()` may use the legacy reconditioning compatibility path and sets `preprocessing_restored_ = False`. That fallback is retained for compatibility but **must not be used as release-grade external-artifact evidence**; the notebook's Section 10 fails closed when it encounters that path.

The E2E notebook exports `artifact.json` and `training_context.parquet` under `outputs/artifact/`, copies them across a fresh filesystem boundary, reconstructs the serving pipeline through the verified no-refit path, and checks prediction equivalence. The E2E export stage also writes `outputs/tabdpt_regressor_artifact.zip`, a deterministic ZIP of exactly those two files (sorted members at the ZIP root, fixed 1980-01-01 timestamp, mode 0644), and prints its SHA-256 as the trusted digest. Section 10 does **not** use this run's export: it loads the pinned sample artifact, a release asset exported by a recorded earlier run, checked by its pinned SHA-256; a user may supply their own ZIP with `EXPECTED_ZIP_SHA256`, then unlabelled CSV/Parquet rows by `EXTERNAL_ROWS_PATH` or upload.

Digest and manifest checks establish internal consistency with this repository's contract; they do not authenticate the sender. The release artifact format is Parquet context plus JSON metadata; the ZIP is only a deterministic container for exactly those two files, extracted member by member after its digest check, and no pickle or arbitrary Python-object payload is accepted. Because `training_context.parquet` contains labelled support data, treat an exported artifact with the same confidentiality, licensing, retention, and disclosure controls as its source dataset.
