## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install or repository import. Section 2 of each notebook is `src/tabdpt_regressor_pipeline/{pipeline,artifact,dimer_runtime}.py` verbatim in dependency order (three cells tagged `metadata.dimer.embedded_module`; the only rewrite makes `DEFAULT_WEIGHTS_DIR` working-directory-relative, package-relative `from .pipeline import` lines are removed because the names are kernel globals, and `dimer_runtime.py`'s top-level `__main__` guard is rewritten to `if False:` so the DIMER worker entrypoint cannot execute inside the kernel), Section 3 carries the model identity and the one-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating commit, the package SHA-256 and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when a carried module, the inline manifest, or the inline pins differ from the repository, or when a notebook is not byte-identical to the generator's output for its template.
- **Model acquisition:** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entry that is absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes it and asserts the manifest digest equals the package's `TABDPT_WEIGHT_SHA256`; `from_pretrained(weights_dir=WEIGHTS_DIR, ...)` pins the verified file as the base checkpoint without loading a model (the model is constructed inside `fit` / `load_verified_artifact`). The notebooks' only external dependencies are the pinned PyPI distributions and the Hub at that revision.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/<stem>_input_manifest.json` with the schema, observed table structure and target summary, verdict and one recorded rejection finding; `evaluation_report` (EVAL21) writes `outputs/<stem>_evaluation_report.json` — `sample-sanity` with `mae` / `rmse` / `r2` and the training-mean baseline in the E2E notebook, `not-measurable` (with what labelled data would make the task measurable) in the companion.
- **Artifact-inference companion (§18):** the artifact is supplied from outside the execution (upload, or `ARTIFACT_DIR` for executors) and validated by `validate_artifact_bundle` before any model state is reconstructed; `load_verified_artifact` takes the base checkpoint from the Section 3 snapshot (no network fallback) and the notebook fails closed on the legacy reconditioning path; no artifact is created and no support fitting happens in the companion.
- Regression obligations (Notebook Specification §20.2): the target is validated as finite numeric (and non-constant) before the model runs, MAE and RMSE are reported in target units with R² alongside, and the notebooks state that predictions are point estimates with no uncertainty interval.
- `USE_BYOD` defaults to `False` so the E2E sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the clean-runtime execution requirement; a release review must confirm that a recorded clean run in `../docs/release-verification.md` matches the notebook revision under review before the status is promoted to `Release-grade`.

## Preprocessing and capacity semantics

For TabDPT, `fit()` performs preprocessing fitting plus **in-context support conditioning**, not gradient fine-tuning. The repository feature encoder preserves numeric columns and deterministically maps categorical values, using separate fitted codes for missing and unseen categorical values. Upstream TabDPT uses a training/support-fitted mean imputer for numeric missing values and standard scaling. If encoded feature width exceeds the loaded model's `max_features`, the upstream configured feature-reduction path is surfaced by the tutorials; `context_size` separately limits support rows used during prediction.

The E2E notebook reports input shape/missingness, model feature ceiling, whether feature reduction activates, requested context size, and the effective upper bound on support rows. The artifact-inference notebook reports the same serving-relevant capacity information for an externally supplied artifact and validates new numeric data so non-numeric or infinite values do not silently become imputed values.

## Artifact contract and trust boundary

The reusable DIMER serving state includes the labelled support table, fitted repository encoder state, fitted upstream imputer/scaler state, any fitted PCA basis needed for wide tables, and the exact pinned base-model contract.

`export_artifact_bundle()` emits an explicit v3 release artifact. `validate_artifact_bundle()` checks artifact format/task, fitted preprocessing consistency, support-table path/size/SHA-256, and the declared base-model repository/revision/filename/digest/upstream commit before model loading. `load_verified_artifact()` reconstructs new release artifacts from saved fitted preprocessing state **without fitting those preprocessing statistics again**.

Established older `tabdpt-dimer-context-v3` manifests that predate the additive explicit version/semantics/size fields remain compatible. If such an artifact lacks the complete fitted upstream preprocessing state, `load_verified_artifact()` may use the legacy reconditioning compatibility path and sets `preprocessing_restored_ = False`. That fallback is retained for compatibility but **must not be used as release-grade `ARTIFACT-INFERENCE` evidence**; the companion notebook fails closed when it encounters that path.

The E2E notebook exports `artifact.json` and `training_context.parquet` under `outputs/artifact/`, copies them across a fresh filesystem boundary, reconstructs the serving pipeline through the verified no-refit path, and checks prediction equivalence. The artifact-inference notebook does **not** manufacture its own artifact: the user must supply those files from a separate producing workflow (upload, or `ARTIFACT_DIR`), then provide separate unlabelled CSV/Parquet input for scoring (upload, or `NEW_DATA_PATH`).

Digest and manifest checks establish internal consistency with this repository's contract; they do not authenticate the sender. The release artifact format accepts Parquet context plus JSON metadata and does not accept ZIP, pickle, or arbitrary Python-object payloads. Because `training_context.parquet` contains labelled support data, treat an exported artifact with the same confidentiality, licensing, retention, and disclosure controls as its source dataset.

## Release verification

CI covers notebook JSON/source structure, Python-cell compilation, profile metadata, the standalone carrier and parity checks (`tools/validate_release_assets.py`, `tools/build_notebook.py --check`, `tests/test_notebook_parity.py`), preprocessing/capacity workflow assertions, artifact-contract/no-refit regression tests, and ordinary repository tests. These checks are not evidence that the current Colab model host/runtime/GPU path executes successfully.

The release gate, the executor procedure for both notebooks and the durable execution record live in [`../docs/release-verification.md`](../docs/release-verification.md) (the execution-only gate was tracked in issue #15). Until clean-runtime execution evidence is recorded there for the exact candidate commit of the standalone notebooks, the correct status is **Candidate**, not release-grade.
